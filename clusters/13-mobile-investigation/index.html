Eng plan · two parallel tracks

Don't wait for the AppsFlyer fix to ship the resilience layer. Both happen in parallel.

Track 1 · Root cause (AppsFlyer / OneLink)

  1. Audit OneLink template: confirm deep_link_value contains the invite code; confirm Universal Link domain + Associated Domains entitlement on iOS.
  2. Reproduce the broken iOS fresh-install path with a controlled new code (not GTA6S; avoid noise).
  3. Inspect AppsFlyer SDK callback timing — is onConversionDataSuccess called before or after the splash → permissions → code-entry render?
  4. If timing race: implement the resilience pattern (Track 2) regardless. Don't paper over with a longer splash.
  5. If config bug: fix OneLink + redeploy.

Track 2 · Resilience layer (ID 146)

Independent of root cause. Pattern:

  1. Code-entry screen subscribes to deep-link state. If a valid invite arrives while it's mounted, auto-fill the code field, show "Inviter found: Tony Staehelin," and advance.
  2. If user has already advanced past code-entry to username before invite arrives: route a stale-invite handler that walks back to invited-by with one tap.
  3. Add a manual "I had an invite link" affordance on code-entry — last-resort fallback for users who manually re-enter.

Track 3 · Logging + audit (IDs 144, 145)

  • Add structured logging at: app open, AppsFlyer callback, deep-link parse, invite-code store, route decision, attribution write.
  • Build the historical audit query: users with code_used=skip1 who had any invite-pattern Fullstory events. Quantify the bleed.
  • Build the QA matrix as a reusable test plan in confluence/Notion. Run it pre-release for any deep-link-touching change.

Open product decisions

D-24 · How transparent are we to affected users (Walteria, etc.)?
Option A · Backfill attribution silently + add inviter relationship
Walteria gets credit applied to Tony retroactively. No user-facing comm. Low embarrassment, low surprise. Recommended.
Option B · Send affected users a "we noticed" email + manual acceptance
Most transparent. Heavy: requires building a UI to confirm/decline a backfilled inviter. Probably overkill given the affected user count.
Option C · Don't backfill; only fix forward
Cheapest engineering. Tony's referrals don't get credit; users like Walteria stay attributed wrong. Unfair to inviters.
